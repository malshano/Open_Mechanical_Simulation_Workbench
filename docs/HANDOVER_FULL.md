## 3. How the work was done (the method), and prompt templates

**Method per feature:** (1) create a worktree from staging; (2) a subagent implements it (code, tests, docs, screenshots in a native window), committing as it goes; (3) one light review by a separate subagent (relaxed on 2026-11-28; before that the rule was a reviewer scoring user experience and accuracy 1 to 7, pass at 6.5 or above on both, with rework rounds); (4) merge into staging, run the touched tests, push, close the issue.

**Implementer prompt skeleton** (what worked): WORKSPACE (exact worktree path, branch, base; never edit other folders; do not push; commit locally with sign-off and the two trailers; read CLAUDE.md and CONTRIBUTING.md first; venv python; offscreen Qt tests; one pytest process; commands under about 5 minutes; no OpenFOAM solves unless the issue needs one and then one at a time after checking RAM and processes; only owner-authored issues) + THE ISSUES (paste the issue text and the existing code to build on) + WHAT TO DELIVER (numbered; engine, Qt controls, API/control ids, tests that fail without the change, docs: USER_MANUAL, TECHNICAL_MANUAL, QT_PARITY, MESHING_GUIDE) + UI RULES (consistent with neighbouring controls, plain words, visual cues and drag handles over sliders, Simple/Expert and light/dark, no new modal dialogs) + QUALITY BAR + FINAL REPORT format (per issue what existed, what added, files, test counts, screenshots looked at, what is unproven, commit hashes, nothing outside the worktree touched).

**Reviewer prompt skeleton:** an independent, sceptical reviewer who did not write the code; scores user experience and accuracy 1 to 7 (7 best, 4 barely usable; pass at 6.5 on both); read-only on all repos (scratch under the session scratchpad with a unique file prefix); verify the implementer's claims with own runs (tests, old-code failure check via `git archive staging`, native-window screenshots read as images, accuracy measurements, edge cases); report scores, per-finding evidence ranked MUST/SHOULD/NIT, what was run and not.

**Agent operations:** subagents are resumed with `SendMessage` to their id after a usage-limit cut-off or to send follow-up findings; reports arrive as messages; an idle agent "waiting on background work" can re-send the same report many times, stop it with `TaskStop`. At most two implementers at once (usage limits and machine load). Conflicts when merging branches were small and resolved by keeping both sides (a Python script that replaces the conflict markers with both blocks was used).
